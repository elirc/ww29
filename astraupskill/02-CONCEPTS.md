# Concepts: ownership and state transition

Opening a notification is a constrained update. The recipient boundary decides whether the actor may see the record; the delivery state decides whether opening is legal. A user who is not the recipient should receive the same 404 shape as a missing record, avoiding an existence leak. A notification with only QUEUED or SKIPPED deliveries is visible only to an authorized viewer but cannot transition to opened because no message was sent.

After the delivery update, aggregate status must be refreshed. A notification may become COMPLETED when its deliveries are OPENED; its parent batch may become COMPLETED when all notifications are complete. The service writes an audit event with the opened delivery ids so later operators can trace the transition. The production permission helper distinguishes `notifications:view:any` from `notifications:open:own`; ADMIN access to another recipient still uses the same open operation. The lab uses status read adapters and actual repository status derivation functions, so it demonstrates service ordering rather than database atomicity. It also does not decide whether repeated opens are idempotent; that policy should be explicit before adding a retry endpoint. Read [the source](../src/services/notificationService.ts) and [repository derivation](../src/repositories/notificationRepository.ts) before changing status semantics.
